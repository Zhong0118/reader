# Reader 0.8 及更早版本 → NeoRead 0.9 一次性迁移

这段代码只处理 Reader 更名时的一次性数据交接。固定事件键为 `reader-to-neoread`；完成后更新 NeoRead 版本不会再次复制。开发模式不读取用户的旧 Reader 数据。

## 迁移范围

采用业务数据白名单，按数据归属选择路径：

| 数据       | 范围                                                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 实际书库   | 从旧 `library-location.json` 解析；没有配置时使用 `Reader/library`。复制整个业务书库，包括数据库、WAL、原文、附件及书库内其他持久数据 |
| 旧默认书库 | 自定义书库生效时，仍保留并迁移存在的默认 `library` 副本                                                                               |
| 书库位置   | 读取旧配置，生成指向新书库的 `library-location.json`                                                                                  |
| 代理配置   | 复制 `proxy-settings.json`                                                                                                            |

书库自身的 `reader.lock`、`neoread.lock`、`server.json` 和 `ai-work` 是运行信息，不复制。其余书库内容不按 Chromium 缓存名字过滤；即使业务书库内部有同名目录，也会保留。

Chromium profile、缓存、日志、更新下载、引用连接文件和未识别的应用目录条目不参与新迁移，也不参与新迁移的源数据校验。它们保留在旧目录，不会因为未入白名单而被删除。迁移不需要维护 Chromium 缓存目录名列表，也不引入临时 Electron profile、额外重启或原生启动器。

数据库中的笔记、批注、聊天、翻译与阅读设置随书库迁移。不会整目录搬运浏览器的 Local Storage；旧浏览器数据仍留在原处。现有前端仅对当前来源能访问的旧偏好键做一次性转换，不能承诺跨动态端口恢复这些界面偏好。

## 启动和位置

安装版在正常 Go 服务、代理配置加载和阅读窗口启动前运行迁移。Electron 可以初始化自身 profile，但迁移器只操作所选业务路径。

- 默认书库进入 `NeoRead/library`。
- 应用目录内部的自定义书库保留相对路径，按实际书库目录安装；其父目录的其他文件不复制、不覆盖。
- 外部自定义书库复制到原目录同级的 `NeoRead Library`。自动清理不会删除这个外部旧副本。
- 复制前持有实际旧书库及闲置默认书库的旧锁。已有目标业务数据、离线设备、书库位置变化、路径重叠、损坏配置和所选路径中的符号链接会使迁移停止。
- 书库与应用运行目录完全重合时无法形成独立业务目录，停止并要求手动处理。
- 没有书库、只有代理配置的旧安装可以迁移配置。旧库存在但缺少必要数据库或原文时不会启动空库掩盖问题。

每次复制前检查可用空间并预留 64 MiB。应用业务数据暂存在目标的 `.reader-to-neoread`，外部书库暂存在同文件系统的 `.neoread-migration-<ID>`。重用临时目录前检查归属，逐文件检查写入结果并校验复制前后的 SHA-256。

复制数据库及 WAL 后，在私有副本上执行完整性、外键和原文文件检查，合并已提交的 WAL，再转换为 `neoread.sqlite`。只转换数据库中的旧设置键和必要路径指纹，不修改原文内容，也不修改源数据库。较旧版本缺少的业务表由正常数据库升级创建。

## 一次性记录与旧记录恢复

`migrations.json` 保留 `schemaVersion: 1` 和已有的其他迁移事件。新记录用 `dataOnly: true` 标识这次业务白名单复制，`SourceHash` 仅覆盖所选业务路径，`Entries` 仅记录待启用的业务单元。它不是通用的多版本迁移框架。

| 状态                      | 行为                                                       |
| ------------------------- | ---------------------------------------------------------- |
| 没有旧数据                | 写入 `not-needed / fresh-install`                          |
| 已有 NeoRead 业务数据     | 写入 `not-needed / existing-install`，保护现有库           |
| `copying`                 | 校验临时目录归属后，按白名单重新复制                       |
| `verified`                | 核对业务单元哈希并继续启用，已启用的业务数据必须与清单一致 |
| `completed`、`not-needed` | 跳过迁移，不随应用版本号重置                               |
| 无法识别或损坏的记录      | 停止启动并提示导出诊断，保留原数据                         |

对 0.9.0/0.9.1 的既有记录：

- 旧 `copying` 记录从源库重新复制时采用白名单。
- 旧 `verified` 记录只继续启用含业务数据的条目，其他 profile 条目留在原位置或暂存位置，不再与运行中的 Chromium 争用目录。`GrShaderCache`、`ShaderCache` 及任何不属于业务清单的其他目录均遵守同一规则。
- 旧 `completed` 记录继续有效，不重新迁移。
- 原有 `digestVersion` 0/1 的全目录哈希规则被冻结，仅用于校验历史记录。旧清理记录的引用文件变化，仍通过经过原清单认证的副本核验；无法证明安全时保留旧数据。新记录不使用这套全 profile 校验。

业务数据先验证，再写入 `verified`，然后逐项启用；只有全部业务数据启用后才写入 `completed`。正常服务和阅读窗口在此后启动。桌面退出时取消仍在运行的迁移子进程并等待关闭，主动取消记录为 `migration.cancelled / desktop_quit`。

## 清理旧业务数据

新库与窗口打开后，在 `legacyCleanup.status = pending` 时提供“稍后清理”和“立即清理”。文案明确说明只清理已迁移的旧书库和配置，其他文件保留；旧 Reader App 由用户卸载。

清理使用同一份业务白名单。删除前重新锁定旧书库、校验业务数据，并确认当前库没有使用旧位置。新记录不因缓存、日志、引用凭据或其他未选中文件的变化而失败。

清理不会重命名或递归删除整个 Reader 应用目录，也不会移动持有锁的书库目录。它保持书库锁，将可清理的业务内容移入同级 `.reader-cleanup-<ID>`，再核对隔离后的业务哈希，最后删除。移动或核对失败时尝试回滚；发生中断或无法回滚时保留隔离数据并报告路径，不自动覆盖已有目录。

旧 `Reader` 目录可能保留 Chromium profile、引用连接文件、锁和其他未迁移的内容。Word/WPS 的固定连接路径不受影响。清理失败不会撤销已完成的迁移。

清理选择记录为 `kept`、`deleted` 或 `failed`，后续启动不会自动重复删除。对于此前失败的清理，用户重新确认后可显式重试；不覆盖 `kept` 决定，不跳过路径、锁与数据校验。macOS 默认安装位置示例：

```sh
"/Applications/NeoRead.app/Contents/Resources/bin/neoread-server" \
  --cleanup-reader-data delete --retry-reader-cleanup \
  --reader-data "$HOME/Library/Application Support/Reader" \
  --data "$HOME/Library/Application Support/NeoRead"
```

若发现已有清理隔离目录，保留数据并提示手动检查，避免把中断前后的资料混在一起删除。

## 诊断与验证

迁移期间日志写入 `.migration-logs`，成功后正常日志写入 `logs`；启动失败可直接导出诊断包。日志记录阶段、耗时和受控失败原因，不记录文档内容、凭据、原始错误正文或用户路径。

回归覆盖默认/内部/外部书库、WAL、旧 schema、位置和路径指纹、未知 profile 目录、嵌套库的未选中兄弟文件、源数据变更、旧记录恢复、复制失败重试、清理选择和显式重试。Windows CI 也执行 Reader 迁移与清理用例。安装包实际使用仍需检查真实资料、磁盘故障与中断后的恢复。
